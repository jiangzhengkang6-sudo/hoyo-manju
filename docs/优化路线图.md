# 优化路线图

> 基于当前代码（后端 66 个模块约 2.1 万行、前端 15 个视图约 1.7 万行、25 张表、151 个接口、380 + 140 项测试、0 个 TODO）做的一轮定向评审。
>
> 排序原则不是「技术上最难」，而是**「不做会卡住什么」**：P0 卡部署，P1 卡演进速度，P2 卡体验上限。

---

## 0. 优先级总表

| 级别 | 方向 | 具体动作 | 预期收益 | 改动面 |
| --- | --- | --- | --- | --- |
| **P0** | 安全 | 全站接口补认证与用户隔离 | 从「只能本机自用」变成「可对外部署」 | 中（加依赖 + 中间件 + 迁移） |
| **P0** | 性能 | SSE 从「轮询数据库」改为「进程内广播」 | 常驻 DB 查询从 N 次/秒降到 0 | 小（改 1 个文件） |
| **P0** | 安全 | 启动时校验默认密钥、关闭调试暴露面 | 消除「忘改配置就上线」的风险 | 小（改 config + main） |
| **P1** | 可维护性 | 拆分 3 个后端巨型模块与 2 个前端巨型视图 | 单文件从 1000~2200 行降到 400 行内 | 大（纯移动，不动逻辑） |
| **P1** | 测试 | 补 4 个高频视图的组件测试 | 视图层从 1/15 提到 5/15 覆盖 | 中 |
| **P1** | 性能 | 消除时间线构建中的 N+1 查询 | 50 镜场景 SELECT 从 ~50 次降到 2~3 次 | 小 |
| **P1** | 扩展性 | 供应商注册从硬编码字典改为装饰器注册 | 新增供应商只写一个文件，不改注册表 | 小 |
| **P1** | 扩展性 | 队列支持多实例（Redis 后端） | 从单机 3 并发扩到可横向扩容 | 中 |
| **P2** | 可观测性 | trace_id 串联成一次请求的全链路耗时 | 定位「慢在哪一步」从翻日志变成看一条链路 | 中 |
| **P2** | 安全 | 内容检测从关键词升级为多模态审核 | 拦截准确率提升，减少误杀与漏放 | 大 |
| **P2** | 前端 | 路由级分包与首屏瘦身 | 首屏 JS 从 140KB 降到 ~80KB | 小 |
| **P2** | 体验 | 键盘操作与无障碍 | 高频操作（确认/驳回/切换镜头）可全键盘完成 | 中 |

## 1. P0：不解决就不能对外部署

### 1.1 全站接口没有任何认证与用户隔离

**现状**：`app/api/routes/*` 151 个端点全部无鉴权；`users` 表只有一个固定的 `LOCAL_USER_ID`（"本地创作者"），仅用于挂配额上限。任何能访问 18437 端口的人，都可以创建项目、消耗配额、删除素材、读取全部生成内容。

**为什么现在能跑**：项目定位是单机个人工具，前后端都在本机。

**一旦要做的事**：
1. 加 `Depends(current_user)`：从 `Authorization: Bearer` 或会话 Cookie 解析用户，未登录返回 401；
2. `Project` 增加 `owner_id`（现在只有 `users` 表但项目未关联），所有查询按 `owner_id` 过滤；
3. 关键写操作（导出、删除、改供应商配置）加角色判断；
4. 前端登录页 + 401 拦截跳转。

**预期收益**：从「本机自用」变成「可给他人试用」；也是接云托管（对象存储、CDN）的前置条件。
**成本**：约 6 个文件改动 + 1 个迁移；风险点是历史数据补 `owner_id`。

### 1.2 SSE 每秒轮询数据库

**现状**：`app/api/routes/jobs.py::_sse_stream` 的实现是「每 `POLL_SECONDS` 秒查一次 `event_log`，有新行就推」。每个打开的页面持有一个连接（`stores/episode.ts` 全局一个 + `JobsView` 一个）。

**问题**：10 个标签页 = 10 次/秒的 SQLite 查询常驻；SQLite 是单写者模型，这些读虽走 WAL，但仍会与写事务争抢 `-shm`，任务并发高时表现为「进度条卡顿」。

**建议做法**：
1. 进程内维护一个 `asyncio.Queue` 或 `threading.Condition` 广播器（`services/events.py` 里 `publish()` 已经在同一进程内被调用）；
2. SSE 循环改为「等通知 → 从 DB 拉一次增量 → 推送」，超时才发心跳；
3. DB 只保留「重放历史」职责（`last_event_id` 断线重连仍走 DB）。

**预期收益**：空闲期 DB 查询归零；推送延迟从「最长 1 秒」降到「毫秒级」；多标签页不再线性叠加压力。
**成本**：单文件改动，约 60 行，风险低。

### 1.3 默认密钥与调试暴露面

**现状**：`settings.secret_key` 默认值 `dev-only-change-me-0123456789abcdef`，用于签发素材 URL 与加密供应商密钥；`S3_SECRET_KEY` 默认 `minioadmin`。如果部署时 `.env` 漏配，签名 URL 可被伪造、供应商密钥可被解密。

**建议做法**：
1. `APP_ENV=prod` 时启动校验：`secret_key` 仍为默认值 → 拒绝启动并给出明确提示；
2. 密钥长度与熵下限校验；
3. `/docs`、`/openapi.json` 在 prod 下默认关闭或加保护。

**预期收益**：把「配置遗漏」从运行时隐患变成启动期硬失败。
**成本**：20 行，零风险。

## 2. P1：影响演进速度

### 2.1 巨型模块拆分

| 文件 | 行数 | 现状问题 |
| --- | --- | --- |
| `app/agents/audio.py` | 1312 | TTS + 音色 + BGM + 字幕时间轴全在一起 |
| `app/api/routes/projects.py` | 1120 | 项目、剧集、角色、画风、音色五类端点混装 |
| `app/agents/edit.py` | 1061 | 时间线 + 校验 + 字幕 + 打包 |
| `app/providers/custom.py` | 1027 | 5 家供应商的实现挤在一个文件 |
| `frontend/src/layouts/WorkbenchLayout.vue` | 2189 | 布局、SSE、任务条、门控、侧栏全在一个组件 |
| `frontend/src/views/EpisodeAudioView.vue` | 1971 | 音色、台词、BGM、字幕四块 |

**建议做法**（按收益排序，不动逻辑只搬代码）：
1. `projects.py` → 按资源拆成 `projects/`、`episodes/`、`characters/`、`styles/`、`voices/`（路由前缀不变，前端零改动）；
2. `custom.py` → `providers/vendors/` 每家一个文件，配合注册表改造（见 2.4）；
3. `WorkbenchLayout.vue` → 抽 `useWorkbenchSse`、`TaskBar`、`GateDrawer`、`SideNav` 四个单元；
4. `EpisodeAudioView.vue` → 抽 `VoicePanel`、`DialogueTable`、`BgmCard`、`SubtitleList` 四个子组件。

**预期收益**：单文件 1000+ 行时，改一处要读半天、review 看不出影响面；拆到 400 行内后，改动定位与并行开发都变快。**这是纯重构，风险极低但收益很实**。

### 2.2 视图层测试几乎为零

**现状**：15 个视图只有 `ProjectAssetsView.spec.ts` 1 个；3 个组件有 spec。后端 380 项测试覆盖较密，前端 140 项主要集中在 api 归一、store、少数组件。

**建议做法**：按「用户操作频率 × 数据复杂度」补 4 个：
- `EpisodeShotsView`（候选图选择、批量确认）
- `EpisodeVideoView`（确认/跳过/重试，状态机展示）
- `EpisodeAudioView`（台词表编辑、BGM 范围选择）
- `EpisodeRenderView`（校验失败展示、部分预览入口）

每个视图钉三类断言：数据来了能渲染、按钮打到对的接口、失败时给人话提示。

**预期收益**：视图层是整个项目最容易「逻辑对但接线错」的地方（此前已出现「任务成功但页面不刷新」）。补完后回归成本从「手点一遍」降到「跑一遍」。

### 2.3 时间线构建中的 N+1 查询

**现状**：`agents/edit.py` 中 12 处 `session.get`，其中 6 处在循环内（构建视频轨、音频轨、字幕时逐条取关联对象）。50 个镜头的一集，构建一次时间线要发几十次 SELECT，而时间线在**每次校验、每次预览、每次导出**都会重建。

**建议做法**：
1. 一次性 `IN` 查询把 `MediaAsset`、`Shot`、`AudioTrack` 批量取回，做成字典；
2. 或者给 `build_timeline` 加一层 `@lru_cache`（按 `episode.version` 失效）。

**预期收益**：50 镜场景 SELECT 从 ~50 次降到 2~3 次；时间线接口 P95 明显下降，预览按钮的等待感减弱。

### 2.4 供应商注册是硬编码字典

**现状**：`app/providers/registry.py` 里四张字典（文本/图像/视频/语音）逐条列出工厂函数，新增一家供应商要改 4 处：import、字典、`ProviderKind` 枚举、可能还有前端下拉。

**建议做法**：装饰器注册 —— 每个实现文件顶部写 `@register(ProviderKind.IMAGE, "gemini")`，registry 只维护一个空字典；前端下拉从 `/config/providers` 动态拉。

**预期收益**：新增供应商从「改 4 个文件」变成「加 1 个文件」；第三方扩展不会碰核心代码。这也是把项目从「我的工具」变成「可交付框架」的关键一步。

### 2.5 队列单机，扩容路径未实现

**现状**：`docker-compose.yml` 留了 Redis（`infra` profile），但 `redis` 依赖在代码里从未被 import；任务队列完全依赖 DB 表 + 租约。

**问题**：SQLite 的写锁是全局的，Worker 扩到 3 个以上就开始互相等；跨机器部署直接不可用。

**建议做法**：
1. 先换 PostgreSQL（`DATABASE_URL` 一改即可，ORM 已隔离方言）；
2. 队列抽象出 `JobQueue` 接口（现成实现：DB 版 / Redis Streams 版）；
3. 事件总线同样抽象（进程内广播 / Redis Pub-Sub）。

**预期收益**：从「单机 3 并发」到「多机水平扩展」；也顺带解决 SSE 跨进程推送。

## 3. P2：体验与长期

### 3.1 可观测性：trace_id 有了，但只到「单条日志」

**现状**：每个响应带 `x-trace-id`，错误体里也带；但一次生成涉及「HTTP 请求 → 任务入队 → Worker 执行 → 供应商调用 → 落库」五个阶段，跨越进程边界，目前只能靠时间戳人工串联。

**建议**：把 `trace_id` 写进 `jobs.trace_id` 与 `provider_calls.trace_id`，日志里统一注入；再往上接 OpenTelemetry（FastAPI 与 httpx 都有现成 instrument）。

**收益**：排查「这次为什么慢」从翻三个日志文件变成看一条链路。

### 3.2 内容检测：目前是「关键词 + 素材标记」

**现状**：`agents/safety.py` 做输入关键词检查与素材 `safety_status` 标记，但素材是否合规依赖供应商返回的标记，没有本地二次判定。

**建议**：接一个多模态审核接口（图片/视频抽帧 + 文本），把结果写进 `safety_detail`，并对「供应商说合规但本地判定高风险」的情况做人工复核队列。

**收益**：降低漏放风险；对 AIGC 内容平台来说这是合规硬要求。

### 3.3 前端首屏：路由已分包，但主包仍 140KB

**现状**：`index-*.js` 139.64KB（gzip 54KB），各视图已懒加载。

**建议**：把 Pinia store 与 API 层按域拆分（episode / project / config），首屏只加载壳与登录态；组件库没有引入，这点做得好，继续保持。

**收益**：首屏可交互时间下降约 30%。

### 3.4 键盘操作与无障碍

**现状**：核心操作（确认画面、确认视频、切换镜头）全靠鼠标；`aria-label` 部分有，但焦点顺序、快捷键、弹层焦点陷阱未系统处理。

**建议**：给高频动作加快捷键（`J/K` 切镜、`Enter` 确认、`Esc` 关闭弹层），弹层加焦点锁定，表格加 `role` 与行级可聚焦。

**收益**：高频剪辑场景效率明显提升；也是产品化必经项。

### 3.5 文档与接口契约自动化

**现状**：`docs/API.md` 手写，与代码可能漂移；FastAPI 自带 OpenAPI 但生产环境关闭。

**建议**：以 OpenAPI 为单一事实源，生成前端类型（`openapi-typescript`），手写文档只保留「为什么这么设计」的部分。

**收益**：后端改字段前端立刻编译报错，避免「接口变了页面空白」。

## 4. 现在不建议做的

避免过度设计，这几项在当前阶段投入产出比很低：

| 想法 | 为什么现在不做 |
| --- | --- |
| 微服务拆分 | 单机 3 并发、单用户，拆分只会把「一次函数调用」变成「一次网络调用 + 分布式事务」 |
| 引入 Celery / Kafka | 任务量级是「分钟级 × 个位数并发」，DB 队列 + 租约完全够用；多一个中间件就多一处运维 |
| 自研模型 / 微调 | 当前质量瓶颈在提示词与素材一致性，不在模型能力；微调的成本与迭代速度都不划算 |
| 完整 CI/CD | 个人项目、单机部署，脚本化冒烟（`smoke_http` / `smoke_sse`）已覆盖关键路径；等有协作再上 |
| 前端换框架 / 引组件库 | 现有设计令牌 + 容器查询已经跑通，换库等于重写 UI，收益为负 |

## 5. 建议的执行顺序

如果只有一周，按这个顺序做收益最高：

1. **第 1 天**：SSE 改进程内广播（P0-1.2）+ 默认密钥校验（P0-1.3）—— 两处小改动，当天可见效果；
2. **第 2–3 天**：拆 `projects.py` 与 `WorkbenchLayout.vue` —— 纯搬代码，为后续改动降摩擦；
3. **第 4 天**：N+1 批量化（P1-2.3）—— 预览与校验的等待感直接下降；
4. **第 5 天**：补两个最有价值的视图测试（分镜、音频）；
5. **第 6–7 天**：供应商注册装饰器化（P1-2.4），为接新供应商铺路。

认证与鉴权（P0-1.1）只有在你**打算让别人访问**时才需要，如果继续单机自用，可以永久排在最后——但要清楚这是「本机工具」与「可交付产品」的分界线。
