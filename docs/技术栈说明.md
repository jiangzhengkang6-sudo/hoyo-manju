## 1. Web 框架层

### 1.1 FastAPI —— 不只是「写路由快」

**为什么选它**：这套系统里有一半接口是「提交任务拿 job_id + 轮询/订阅进度」，天然异步；同时需要严格的请求校验（用户输入的提示词、时长、镜号都可能越界）和统一错误体。FastAPI 的 Pydantic 集成 + 依赖注入 + `StreamingResponse` 正好覆盖。

**项目里的实际用途**：

| 用途 | 实现位置 | 说明 |
| --- | --- | --- |
| REST 接口 | `app/api/routes/*.py`（11 个路由模块） | 项目 / 剧集 / 剧本 / 分镜 / 生成 / 音频 / 渲染 / 导出 / 供应商 / 配置 / 审计，共 151 个端点 |
| SSE 实时流 | `app/api/routes/jobs.py::_sse_stream` | 用 `StreamingResponse` 手写 `text/event-stream`，支持 `last_event_id` 断线重连与心跳注释行 |
| 请求级事务提交 | `app/main.py::RequestSessionMiddleware` | 拦截 `http.response.start` 再提交，保证「响应发出时数据已落库」 |
| 统一错误体 | `app/core/errors.py` + 全局异常处理器 | 所有错误返回 `{error:{code,message,details},trace_id}`，`trace_id` 同时写响应头，便于按请求排查 |
| 静态托管 | `app/main.py` | 生产模式直接托管 `frontend/dist`，单进程即可交付，同时保留 SPA 兜底路由 |

**踩过的坑（写进代码注释了）**：

- 用 `yield` 依赖做提交会在响应之后才执行，实测约 60% 的请求出现「刚写完就查不到」。改成中间件拦 `http.response.start` 才稳。
- 错误体里的 `details` 不能直接塞 `datetime`（`json.dumps` 会抛 `TypeError`），现在统一走 `jobs.jsonable()` 递归转换。

### 1.2 Uvicorn —— 两种跑法

- 开发/单机：`uvicorn app.main:app`，同时内嵌一个线程池 Worker（默认并发 3），一个进程就能跑完整闭环。
- 扩容：`python -m app.worker.runner` 单独起 Worker 进程，API 侧把 `ENABLE_EMBEDDED_WORKER=false`，共用同一个 SQLite（WAL）与存储目录。

### 1.3 Pydantic v2 —— 同时充当「LLM 输出的安全网」

这是项目里最容易被低估的一处用法。真实 LLM 不会严格照抄枚举值：让它输出 `camera_movement: "推镜头"`、`"pan"`、`"固定机位"`，严格校验会让整条剧本生成失败。

于是给分镜模型加了 `mode="before"` 的归一化校验器：

```python
@field_validator("camera_movement", mode="before")
@classmethod
def _normalize_camera(cls, v: Any) -> Any:
    # 「推镜头 / pan / 固定机位」→ 规范枚举；认不出退回默认值，而不是报错
    return normalize_enum(v, CAMERA_MOVEMENTS, CAMERA_ALIASES, "固定")
```

这样一条剧本里偶尔一个字段跑偏，不会把整次生成（和已花的钱）废掉，而是落到默认值继续走。回归用例在 `tests/test_enum_normalization.py`。

`pydantic-settings` 则把 80+ 项配置（供应商密钥、并发、超时、单价、门控开关）集中在 `app/core/config.py`，`.env` 覆盖，避免散落的 `os.getenv`。

## 2. Agent 编排：LangGraph

### 2.1 为什么是图，不是链

漫剧生产不是「一次调用出结果」，而是：剧本 → 角色 → 分镜 → 出图 → 出视频 → 配音 → 字幕 → 合成 → 导出，中间有 **6 道人工确认**（剧本 / 角色 / 分镜画面 / 视频成本 / 视频 / 导出）。任何一道没确认，后面都不能往下走；用户可能第二天才回来继续。

这三点直接排除了「一条链跑到底」：

1. **需要中断**：`interrupt()` 暂停等人；
2. **需要恢复**：`SqliteSaver` checkpoint 把状态存盘，进程重启后还能从断点继续；
3. **需要按节点重试**：某个镜头的图生成失败，只重跑该节点，不重跑整条（也不会重复扣费）。

### 2.2 项目里怎么用的

| 能力 | 实现 |
| --- | --- |
| 图组装 | `app/workflow/graph.py`：`StateGraph(WorkflowState)`，21 个节点，其中 6 个是 `node_gate_*` |
| 状态持久化 | `langgraph-checkpoint-sqlite` 的 `SqliteSaver`，落在 `data/checkpoints.db`，与业务库分离 |
| 中断与恢复 | `app/workflow/engine.py`：捕获 `GraphInterrupt`，恢复时用 `Command(resume=...)` |
| 节点实现 | `app/workflow/nodes.py`：每个节点只做一件事，内部调用对应 Agent（story/image/video/audio/edit） |
| 降级引擎 | `app/workflow/fallback.py`：如果环境没装 langgraph，自动切到等价的轻量状态机，接口不变 |

**降级设计是刻意的**：个人项目经常在「没有完整依赖」的环境里演示（比如评审机器只装了基础包）。有 fallback 之后，`ENABLE_LANGGRAPH=false` 也能把流程走完，只是少了 checkpoint 续跑能力。

## 3. 数据层

> 这一层只干一件事：**把一次生成过程中产生的所有东西（内容、素材、任务、钱、审计）可靠地记下来，并且保证它们之间不会互相矛盾。**
>
> 之所以值得单开一节，是因为这个项目的数据层踩过的坑，几乎都和「什么时候提交」有关——而不是 SQL 写得对不对。

### 3.1 先看清有哪些数据

25 张表，按职责分 7 类（`app/db/models.py`）：

| 类别 | 表 | 存什么 | 主要写入方 |
| --- | --- | --- | --- |
| 账号与内容 | `users` `projects` `episodes` `story_documents` `shots` `character_assets` `style_assets` `shot_character_refs` `voices` | 项目、剧集、剧本、分镜、角色卡、画风、音色 | 用户操作 + 剧本 Agent |
| 素材 | `media_assets` `audio_tracks` `subtitle_cues` | 图片/视频/音频文件记录、音轨、字幕条 | Worker（生成完成后） |
| 编排与任务 | `workflow_runs` `workflow_node_logs` `jobs` `entity_versions` `event_log` | 工作流运行、节点日志、异步任务、版本快照、事件流水 | 编排层 + Worker |
| 成本 | `cost_ledgers` `price_book` | 每一笔预留/结算/释放、单价表 | 任务创建与收尾 |
| 供应商 | `provider_settings` `provider_calls` | 供应商配置（密钥加密）、每次调用的实际消耗 | 设置页 + Provider 层 |
| 治理 | `approvals` `audit_logs` `safety_appeals` | 人工确认记录、审计、内容拦截申诉 | 门控 + 导出 |
| 交付 | `exports` | 预览/导出记录与清单（manifest） | 渲染任务 |

**先记住三个特征**，后面的设计都由此而来：

1. **写多读少**：一次 6 镜的生成，会产生 6 条素材 + 6 条音轨 + 十几条任务/账本记录，但用户很少反复查历史。
2. **一次操作跨多张表**：点一次「生成画面」，要同时写 `jobs`（任务）、`cost_ledgers`（预扣钱）、之后写 `media_assets`（图）和 `jobs.result_ref`（结果）。
3. **有并发，但很低**：Worker 默认并发 3，同一时刻最多 3 个任务在写库。

### 3.2 一条生成请求的完整数据流（理解这一层的关键）

以「一次给 6 个镜头生成画面」为例，数据是这样流动的：

```
① 用户点「生成画面」
   POST /episodes/{id}/generate/images
        │
        ├─ 写 jobs        status=QUEUED，记录预留金额
        └─ 写 cost_ledgers amount=-N，kind=RESERVE（先扣住钱）
        │
        ▼  ← 这一步必须「提交」后才返回 job_id
② 前端拿到 job_id，开始轮询 / 订阅 SSE
        │
        ▼
③ Worker 抢到任务（条件 UPDATE 把 status 改成 RUNNING）
        │
        ├─ 逐张调供应商出图
        ├─ 每出一张 → 写 media_assets（文件记录）
        └─ 全部完成 → 写 jobs.result_ref（结果摘要）+ status=SUCCEEDED
                      写 cost_ledgers 两条：SETTLE +实际花费、RELEASE -剩余预留
        │
        ▼
④ 前端收到 SSE 的 job.succeeded，重新拉分镜列表 → 看到新图
```

这条链路里有两个「必须提交」的时刻，如果漏掉任何一个，就会出现「数据看起来丢了」：

- **①之后**：不提交就返回 job_id，前端马上轮询会查不到这条任务（`NotFound`）。
- **③中间**：一张图已经存盘、也写进了 `media_assets`，但任务状态还没变；如果这时进程崩了，就变成「有图但任务永远 RUNNING」。

### 3.3 SQLAlchemy：把「改 Python 对象」翻译成「改数据库」

先分清三个概念，很多人卡在这里：

| 概念 | 是什么 | 在本项目里对应 |
| --- | --- | --- |
| **模型（Model）** | 一个 Python 类 ↔ 一张表；类属性 ↔ 列 | `class Job(Base)` |
| **会话（Session）** | 一次「工作单元」：暂存你对对象的修改，攒着一起发 | `SessionLocal()` / `session_scope()` |
| **事务（Transaction）** | 一组 SQL，要么全成功、要么全失败 | `session.commit()` 提交，`rollback()` 撤销 |

模型长这样（`Mapped[...]` 是 SQLAlchemy 2.0 的写法，把类型写进代码，IDE 和静态检查都能用）：

```python
class Job(Base, TimestampMixin):
    __tablename__ = "jobs"
    id: Mapped[str] = mapped_column(String(48), primary_key=True)
    type: Mapped[str] = mapped_column(String(32), index=True)      # IMAGE_GENERATION …
    status: Mapped[str] = mapped_column(String(24), default="QUEUED")
    input_json: Mapped[dict] = mapped_column(JSON, default=dict)    # 任务参数
    result_ref: Mapped[dict] = mapped_column(JSON, default=dict)    # 任务结果
    cost_reserved_cents: Mapped[int] = mapped_column(Integer, default=0)
```

**关键点：你改的不是数据库，是内存里的对象。**

```python
job.status = "SUCCEEDED"   # 此时数据库里还是 RUNNING，一个字节都没变
session.flush()            # 这时才发出 UPDATE 语句（但还没提交）
session.commit()           # 真正落盘，事务结束
```

三个动作的区别（这是全文最该记住的一张表）：

| 动作 | 做了什么 | 失败/撤销后 |
| --- | --- | --- |
| `flush()` | 把内存改动翻译成 SQL 发给数据库，但**不提交** | 还能 `rollback()` 撤销 |
| `commit()` | 提交事务，改动**永久生效** | 不可撤销 |
| `rollback()` | 丢弃本次事务里所有未提交的改动 | 数据库回到事务开始前 |

**本项目的两条提交约定**（这是和普通 CRUD 项目最不一样的地方）：

1. **HTTP 请求路径：业务代码不写 `commit()`**，由 `RequestSessionMiddleware` 在响应即将发出时统一提交。
   原因很现实：早期用 FastAPI 的 `yield` 依赖做提交，它是在**响应返回之后**才执行，导致约 60% 的请求出现「刚创建的项目，跳转详情页 404」。改成中间件拦截 `http.response.start` 才稳定。
2. **Worker 路径：必须手动提交**，因为一个任务要跨两个阶段——「业务产物落库」和「任务状态变更」。这两个阶段之间如果崩了，我们希望产物保住、任务可以被重试，而不是全部回滚。

另外 `SessionLocal` 配了 `expire_on_commit=False`：提交后对象不失效，可以直接继续用（否则每次 commit 后读属性都会悄悄再查一次库）。代价是**对象可能拿着「提交前的旧值」**——成本结算的负预留 bug 就是这么来的（见 §3.5）。

### 3.4 真实事故：任务卡在 RUNNING 100%

这是数据层最值得讲的一个案例，完整还原一下：

```
现象：BGM 生成完成，音轨已经挂到时间线、素材文件也在，
     但任务列表里一直显示「运行中 100%」，重试按钮点不动。

排查：① 查库 → job.status 仍是 RUNNING，但 media_assets / audio_tracks 已有记录
     ② 抓线程栈 → Worker 线程空闲，说明任务函数早就返回了
     ③ 说明「任务已完成」的那次 commit 失败了
```

根因是三层叠加：

```python
# 1) 业务代码把结果塞进 JSON 列
job.result_ref = {"track": track_to_dict(...), ...}
#    track 里嵌了 media.to_dict()，其中 created_at 是 datetime 对象

# 2) commit 时 SQLAlchemy 要把 dict 序列化成 JSON 字符串
#    → TypeError: Object of type datetime is not JSON serializable

# 3) 这次 commit 同时带着 status=SUCCEEDED
#    → 事务回滚，连状态一起撤销；但媒体文件早在另一个已提交的事务里了
```

修复三处，缺一不可：

| 修复 | 位置 | 作用 |
| --- | --- | --- |
| `jsonable()` 递归转换（datetime → ISO、Enum → value） | `app/services/jobs.py` | 从入口保证写进 JSON 列的永远是纯数据类型 |
| 异常分支先 `session.rollback()` | `app/services/executor.py` | 否则 session 停在 `PendingRollback` 状态，后面写「失败原因」会二次抛错，任务永久卡住 |
| 回归用例 | `tests/test_job_result_jsonable.py` | 端到端跑一单 BGM 任务，断言状态必须到 SUCCEEDED |

**为什么这条值得反复讲**：它同时踩中了「JSON 列的类型限制」「事务的原子性」「提交时机」三个点，而且现象（任务卡住）和原因（序列化失败）离得非常远。

### 3.5 SQLite（WAL）：为什么这个项目够用

**先说结论**：单机、单人、低频写入的场景，SQLite + WAL 完全够；它省掉的是一个必须常驻、必须备份、必须监控的数据库服务。

**WAL 到底解决什么**：

| 模式 | 写的时候 | 读的时候 |
| --- | --- | --- |
| 默认（rollback journal） | 锁住整个库 | 被写阻塞，读不到 |
| **WAL** | 写进单独的 `-wal` 文件 | **照常读旧快照**，不被阻塞 |

对本项目意味着：用户在前端翻分镜列表（读）不会被后台正在写任务记录的 Worker 卡住。代价是多了 `-wal` 和 `-shm` 两个文件，以及「同一时刻仍然只能有一个写者」。

连接建立时设了三个 PRAGMA（`app/db/session.py`）：

```python
cur.execute("PRAGMA journal_mode=WAL")     # 读写不互斥
cur.execute("PRAGMA foreign_keys=ON")      # 外键约束真的生效（SQLite 默认是关的）
cur.execute("PRAGMA busy_timeout=30000")   # 撞上写锁时等 30 秒，而不是立刻报错
```

`busy_timeout` 是关键：没有它，两个 Worker 同时写就会直接抛 `database is locked`，而这种错误在业务上完全没必要暴露给用户。

**多 Worker 怎么不抢同一个任务**：不是「先查有没有任务，有就执行」（两个 Worker 会同时查到同一条），而是用一条带条件的 UPDATE 让数据库来裁决：

```sql
UPDATE jobs SET status='RUNNING', lease_owner='worker-1', lease_expires_at=now+300s
WHERE id=? AND status IN ('QUEUED','RETRYING') AND (lease_expires_at IS NULL OR lease_expires_at < now)
-- 返回 rowcount=1 才算抢到，=0 说明别人先抢走了
```

这就是所谓的「租约（lease）」：谁抢到谁负责，超时没续上就视为放弃，别人可以接手。Worker 崩了任务不会永久卡死。

**什么时候该换 PostgreSQL**：并发 Worker 稳定超过个位数、或需要多机部署时。换法只是改 `DATABASE_URL`——所有查询都走 ORM，没有写死的 SQLite 方言。

### 3.6 Alembic：数据库的「版本管理」

**它解决什么**：代码可以 git 回滚，数据库结构不行。加了字段、改了类型、建了新表，别人的库和你不一样，线上和你本地也不一样。

`init_db()` 里的 `create_all` 只会**建不存在的表**，不会改已有表——所以任何结构变更都必须写成迁移文件（仓库现有 8 个 revision）。

日常三个命令：

```bash
alembic revision --autogenerate -m "add line_index to audio_tracks"   # 生成迁移脚本
alembic upgrade head                                                  # 应用到最新
alembic downgrade -1                                                  # 回退一步
```

两个真踩过的坑：

1. **开发库的 `alembic_version` 是空的时候，直接 `upgrade head` 会把初始迁移重放一遍**，报 `table already exists`。正确做法是先 `alembic stamp <上一个 revision>` 告诉它「你已经在这了」，再升级。
2. **给已有表加 NOT NULL 列必须带 `server_default`**，否则存量行无法补值，迁移直接失败（例：`audio_tracks.source` 默认 `'tts'`、`voice_speed` 默认 `'1.0'`）。

### 3.7 一句话总结这一层

> 模型负责「长什么样」，Session 负责「攒着改」，事务负责「要么全成要么全不成」，迁移负责「结构怎么变」。
>
> 而这个项目 90% 的数据问题，都出在**「什么时候提交」和「提交失败之后怎么办」**上——不是 SQL 写错，是事务边界没想清楚。

## 4. 异步任务与实时事件

### 4.1 自研任务队列 —— 为什么不用 Celery

不是「 reinvent the wheel 」，而是三笔账算下来不划算：

1. AI 生成任务的特点是**单任务耗时长（几十秒到几分钟）、并发极低（3~5）**，不需要高吞吐的 broker；
2. 任务状态本来就要落库（前端要查、要重试、要审计），Celery 的 result backend 等于再存一份；
3. 项目要求「clone 下来就能跑」，多一个 Redis 就多一道部署门槛。

**实现要点**（`app/services/jobs.py` + `app/worker/runner.py`）：

| 能力 | 做法 |
| --- | --- |
| 抢占 | 条件 `UPDATE ... WHERE status IN (CREATED, QUEUED, RETRYING) AND lease_expires_at < now`，用 `rowcount` 判断是否抢到 |
| 防重复执行 | 租约（`lease_owner` + `lease_expires_at`），Worker 崩溃后租约过期可被重新领取 |
| 重试 | 可重试错误按**指数退避**（5s → 10s → 20s，上限 60s）重新入队，预留在多次尝试间保持不变 |
| 幂等 | 生成类接口的幂等键带时间桶（如 5 秒），重复点击返回同一个任务而不是重复扣费 |
| 取消 | 协作式：批处理循环里逐镜调用 `cancel_probe(job_id)`（用独立 session 读，避免污染主事务），只有真的提前停下才标 CANCELLED |

### 4.2 SSE —— 让「几分钟的等待」有反馈

手写 `StreamingResponse`（没有用 `sse-starlette`），原因是要精确控制三件事：事件格式（`id/event/data`）、心跳注释行（防代理超时）、`last_event_id` 重连补发。

事件类型：任务状态变更、任务成功/失败/取消、素材创建、门控待确认、字幕/音轨变更。

前端对应 `useSse()` 组合式函数：URL 回调签名为 `(lastEventId) => string | null`，断线后自动带上最后事件 ID 重连。Vite 开发代理里专门关掉了 SSE 的缓冲（`cache-control: no-cache, no-transform` + `x-accel-buffering: no`），否则进度条会「攒一批再一起跳」。

## 5. 供应商接入层

### 5.1 httpx —— 一套出网策略管住所有供应商

所有供应商共用一个异步客户端封装，重点不在「发请求」，而在**统一超时、统一代理策略、统一网络错误文案**：

`app/providers/net.py` 解决了一个很隐蔽的问题：IDE / 沙箱 / 终端常把 `HTTP(S)_PROXY` 注入成本地代理，对境外域名直接回 502，看起来像「供应商挂了」。于是加了 `PROVIDER_PROXY_URL` 策略（`direct` 强制直连 / 指定代理 / 代理没起时自动退回直连），并把异常翻译成人话：

> 「连不上 maas.qianwenaiapi.com（网络不可达或被拦截）：[Errno 11001] getaddrinfo failed。请检查网络/代理；若该域名在本地无法访问，换一个可达的供应商即可」

### 5.2 统一 Provider 抽象 —— 把三种完全不同的协议抹平

8 家供应商的接口形态差异很大：

| 形态 | 代表 | 差异点 |
| --- | --- | --- |
| OpenAI 兼容 | DeepSeek / OpenAI | `/chat/completions`，同步返回 |
| 通义 MaaS | qwen TTS / Audiogen | 文本放 `input.text_prompt`，回 `output.audio.url`，**不认 voice/speed** |
| 异步任务网关 | toapis（Gemini 图 / Seedance 视频） | 提交拿 `task_id` → 轮询到 `completed` → `result.data[0].url` |

`app/providers/base.py` 定义统一能力描述（`ProviderCapabilities`：模型、计价单位、单价、时长范围、预估延迟）与统一结果（`ProviderResult`：ok / data / artifacts / usage / cost_cents）。

上层完全不感知差异：`resolve(ProviderKind.SPEECH, session)` 拿到当前配置的供应商，调用 `synthesize()` / `generate_json()` / `generate_video()` 即可。**换供应商只改配置，不改业务代码**——这是「8 家可插拔」的实际含义。

### 5.3 熔断与兜底

- **熔断**（`app/services/degraded.py`）：同一类依赖连续失败到阈值就暂停该类新任务（返回 503 并说明原因），已有素材的预览/导出不受影响；成功一次即自愈清零。
- **申诉**：被熔断后管理员可提交申诉，只有显式 `resolve_appeal(APPROVED)` 才放行，避免「重试把熔断刷开」。
- **Mock 供应商**：密钥缺失时注册表自动回退 Mock，能生成占位图/占位音频/占位视频。意义是**没有一分钱预算也能跑通全链路**（CI、演示、新同事上手都靠它）。

## 6. 媒体与存储

### 6.1 FFmpeg —— 这个项目真正的「渲染引擎」

`imageio-ffmpeg` 只用来拿到可执行文件路径（免装系统级 FFmpeg），真正干活的是大量命令行编排，集中在 `app/services/render.py` 与 `app/services/audio_fx.py`：

| 场景 | 做法 | 关键点 |
| --- | --- | --- |
| 多镜头拼接 | `concat` + `xfade` 转场 | `fps` 滤镜必须放在每条 `-vf` 链**最末尾**，否则 `xfade` 报 `current rate of 1/0` |
| 静态图转片段 | `-loop 1 -t <duration>` + `zoompan` | 时长以剧本为准，长图自动裁切填充 |
| 多轨混音 | `adelay` + `amix` + 静音底座 | 用 `anullsrc` 保住总时长，否则音轨比视频短会被截断 |
| 台词/BGM 音量 | `volume` + `afade` 淡入淡出 | 淡入淡出按**音频时长**收敛（4 秒垫乐不能用 1.5 秒淡出，否则等于没声音） |
| 字幕 | `drawtext` | 中文需要显式指定字体；`enable='between(t,...)'` 控制出现区间 |
| 变速不变调 | `atempo` 链 | 单级 `atempo` 只支持 0.5~2.0，超范围要拆多级 |
| AIGC 标识 | `drawtext` 固定角标 + `-movflags +use_metadata_tags` | 导出与预览都必须带，不提供关闭 |
| 单镜裁剪 | `-t <seconds>` | 供应商按自然长度出片（实测要 4 秒给 8 秒），裁掉多余部分避免压到下一镜 |

**踩过的坑（都已写进注释）**：

- 供应商返回的 WAV 头是占位值（`nframes=536870886`，浏览器解析成 10 小时），必须过一遍 FFmpeg 重编码重写头部；否则播放器时长错乱、进度条不可拖。
- 台词 TTS 不支持 `speed` 参数，语速只能在本地用 `atempo` 实现（同时保证音高不变）。
- 渲染结算要取 `manifest["duration_ms"]`，不是 `total_duration_ms`（两者在转场重叠时不同）。

### 6.2 Pillow —— 两个不起眼但必要的用途

1. **图片尺寸探测**：供应商返回的图不一定符合项目画幅，合成前校验比例（偏差 >2% 给 warning），避免成片被拉伸。
2. **Mock 出图**：无密钥环境下生成带文字的占位图，保证前端候选图、确认流程都能走通。

### 6.3 存储抽象 —— 两条铁律

`app/services/storage.py` 提供 `Storage` 抽象与两个实现：`LocalStorage`（本地磁盘）与 `S3Storage`（boto3，可选 MinIO）。

**铁律一：素材一次写入、永不覆盖。**

供应商产物文件名是「每批重新计数」的（`gemini_1.png`、`video_1.mp4`）。直接拿它当存储键，同一天的第二次生成就会覆盖第一次的文件——而数据库仍指向旧记录。线上表现就是**「主角的立绘变成了另一个角色」**。

修复分三层：

```python
# 1) 存储层独占创建，已存在就抛冲突
open(path, "xb")

# 2) key 里带随机后缀，撞名自动重试
key = f"{date}/{stem}_{token_hex(4)}{suffix}"

# 3) 落库前算 sha256，配套校验脚本定期核对文件与记录
python scripts/check_media_integrity.py --mark-stale
```

**铁律二：交付给浏览器的地址必须支持 Range。**

`/media/{id}/content` 与 `/storage/signed/{token}` 都实现 `Range` → `206 Partial Content`。否则 Chrome 拖进度条失败、Safari 直接黑屏。

签名 URL 用 HMAC-SHA256（`app/core/security.py`），默认 30 分钟过期，避免把内部路径直接暴露给前端。供应商密钥用 `cryptography.Fernet` 加密后存库。

## 7. 前端

### 7.1 Vue 3.5 + `<script setup>` —— 按「制作阶段」组织页面

前端不是常见的 CRUD 后台，而是**一条制作流水线的操作台**：故事与剧本 → 角色 → 分镜 → 视频 → 音频字幕 → 预览导出。因此路由与页面直接对应阶段（`src/views/Episode*View.vue`），每页顶部有阶段指示与「当前需要你确认什么」。

选 Composition API 的原因很实际：`useSse`、`useJobWatcher`、`useAutosave` 这些横切逻辑要跨页复用，组合式函数比 mixin 干净得多。

### 7.2 TypeScript 5.6 + vue-tsc —— 类型即接口契约

- 后端返回结构全部在 `src/types/index.ts` 建模（90+ 个接口模型）。
- **前端不信任后端形状**：`shot_json` 嵌套字段在 `api/shots.ts::normalizeShot()` 摊平，角色素材的 `id` / `media_id` 在 API 层归一。页面组件只拿「已经整好形」的数据。
- `vue-tsc --noEmit` 进 CI，模板里的表达式也会被检查（`{{ shot.nonexistent }}` 编不过）。

### 7.3 Vite 6 —— 开发与生产是两套

| 模式 | 做法 |
| --- | --- |
| 开发 | `vite dev`（15731），`/api` 代理到后端 18437，SSE 单独关缓冲 |
| 生产 | `vite build` 产出 `dist`，由 FastAPI 直接托管，单进程交付 |

**踩坑**：改完前端如果只重启后端，页面还是旧界面——因为后端托管的是 `dist` 里的旧构建产物。这条已经写进 README 与开发流程。

### 7.4 Pinia —— 四个 store，各管一摊

| store | 职责 |
| --- | --- |
| `episode` | 当前剧集、分镜列表、工作流状态、任务快照、镜头勾选 |
| `project` | 项目列表与当前项目、画幅比例 |
| `config` | 后端下发的枚举与上限（`/config/limits`）、预设、币种 |
| `toast` | 全局轻提示与错误通道 |

关键约定：**枚举与上限不从后端裸透**，统一走 `config` store 映射成中文；界面上不出现 `epi_/med_/voc_` 原始 id、API 路径、签名 URL。

### 7.5 设计令牌 + 容器查询 —— 为什么不是媒体查询

- `src/styles/tokens.css`：颜色（暖墨黑 + 黄铜）、字号（11/12/13/14/16/19/24）、间距（4/8/12/16/20/24）、圆角、字体族。组件里禁止写裸数值。
- `base.css` 只提供一次 `.page` / `.page-head` / `.stage` / `.two-col`，视图里不再重复定义。
- **两栏布局用 `container-type: inline-size` 判断宽度**，不是视口媒体查询：中间内容区被侧栏挤压后只有约 1000px，按视口判断会在 1440px 屏幕上误判成「宽屏」而挤爆版式。

### 7.6 Vitest 2 + jsdom + Vue Test Utils

140 项用例，重点不在覆盖率数字，而在**钉住几类容易悄悄坏掉的接线**：

- API 归一函数（`normalizeShot`、候选图 `id/media_id` 兼容）
- store 的事件处理（手动喂 SSE 事件，断言状态流转）
- 关键组件（媒体缩略图灯箱、候选图选择、任务条重试/取消）
- 视图接线（数据来了能不能渲染、按钮点击打到对的接口）

jsdom 缺 `matchMedia` / `URL.createObjectURL`，在 `vitest.setup.ts` 里补；`Teleport to="body"` 的弹层要查 `document.body`。

## 10. 技术栈与真实问题的对照表

这张表可能是全文最实用的部分：每一行都是这个项目里**真的发生过**的问题，以及最终靠什么技术解决。

| 问题 | 涉及技术 | 解决方式 |
| --- | --- | --- |
| LLM 输出非法枚举导致整条剧本失败 | Pydantic v2 `mode="before"` | 别名归一 + 兜底默认值，单字段跑偏不影响整次生成 |
| 同一句台词生成两次 / 中间失败导致整体串位 | SQLAlchemy + 音频模型 | 音轨加 `line_index`，按序号对位而不是按毫秒下标 |
| 主角立绘被后续角色顶替 | 存储层 + 文件系统语义 | `open(..., "xb")` 独占创建 + 随机后缀 + sha256 校验脚本 |
| 视频在浏览器黑屏 / 拖不动进度条 | HTTP Range | `206 Partial Content` + 正确的 MIME |
| 供应商 WAV 头是占位值，播放器显示 10 小时 | FFmpeg | 强制重编码重写头部 |
| 语速调了没反应 | FFmpeg `atempo` | 供应商不认 speed，本地变速保持音高 |
| 结算出现负预留 | 成本台账 | 改用台账口径 `outstanding_reserved()`，不用内存旧值 |
| 任务永久卡在 RUNNING 100% | SQLAlchemy JSON 列 | 统一 `jsonable()` 转换 + 异常分支先 `rollback()` |
| 取消按钮「点了没反应」 | 任务队列 | 批处理循环逐镜 `cancel_probe`，独立 session 避免长事务 |
| 短镜头垫乐压到下一镜 | FFmpeg + 时间线 | 按镜头窗口 `-t` 裁剪，淡入淡出按长度收敛 |
| 预览必须等全部镜头就绪 | LangGraph 之外的编排层 | `build_timeline(only_ready=True)` 剔除未就绪镜头并重映射字幕/BGM |
| 境外供应商偶发 DNS 失败被判死 | httpx + 重试策略 | Provider 内就地重试连接类错误，任务级改指数退避 |

## 11. 如果继续演进，技术栈会怎么变

不是为了显得有规划，而是记录当前取舍的边界：

1. **数据库**：并发 Worker 上到两位数或要跨机部署时 → PostgreSQL（ORM 已隔离方言）。
2. **队列**：多实例时 → Redis Streams 或直接换 Celery，`jobs` 表保留为审计与状态源。
3. **Agent 编排**：需要「模型自主决定下一步」而不是固定图时 → 引入工具调用（function calling）与 ReAct 循环；当前是确定性图，更适合生产交付。
4. **存储**：素材量上来后 → 对象存储 + CDN，签名 URL 已有实现。
5. **可观测性**：目前靠 `trace_id` + 审计表 + 结构化日志；下一步接入 OpenTelemetry，把「一次生成」的耗时拆到供应商维度。
